# Doom 640×400 renderer profile — 2026-08-22

Status: retained measurement and optimization evidence. This is not a promise
that 640×400 is the default or currently meets the gameplay cadence.

## Question

Would doubling the logical framebuffer from 320×200 to 640×400 remain
playable, and which Freelang operations dominate when it does not?

`games/doom-profile.flx` drives the real E2M1 map, texture, world, combat, view
and scaled-status operations for a fixed number of 640×400 frames without GUI
or audio wait. `tools/profile.js` builds the existing symbol-rich assembly
oracle and samples that exact workload with macOS `sample`.

## Evidence

- The unmodified 640 live path rendered at about 82 ms/frame. Presenter and
  simulation time rounded to zero in the frame diagnostic; render owned the
  slowdown. The frame-coupled simulation therefore appeared in slow motion.
- The initial 120-frame production workload took 9.91 s real / 9.88 s user and
  produced checksum `4950`.
- Top application leaves were `flx___vsop_plus__dispatch`,
  `flx_doom_view_textured_panel`, `flx_doom_view_draw_planes`, dynamic field
  lookup, and checked raw-buffer access. Monster/world simulation was not hot.
- Hoisting stable atlas/work fields out of the three pixel loops reduced field
  lookup leaf samples from 329 to 135 and the workload to 9.88 s real / 9.40 s
  user, with checksum `4950` unchanged.
- Residual numeric `+` had soundly escaped static specialization but paid for
  every heap-shape predicate before the integer fallback. Value shapes are
  disjoint, so the generated dispatcher now tests primitive int+int first; a
  declared int+int overload is also ordered first and remains authoritative.
  Its structural specialization/overload gate passes 9/9.
- The final workload took 9.38 s real / 8.90 s user with checksum `4950`.
  The rebuilt live path fell from 82 to 70 ms/frame (about 12 to 14 fps). This
  is a real roughly 15% frame-time win, but not a playable 60 fps result.
- The next Doom-local pass precomputes Q32 row reciprocals and column slopes
  once per resolution, retains the already resolved sky texture, and caches
  the per-column sky offsets. One-step exact quotient correction preserves the
  prior integer division result rather than accepting fixed-point drift.
  Three comparable 120-frame user-time runs fell from a 9.32 s mean
  (9.26/9.26/9.43) to 9.03 s (9.07/8.99/9.03), about 3.1%, while checksum
  `4950` remained unchanged.
- `VIEW-1` replaces each admitted raster site's three checked byte writes with
  one explicit little-endian RGBX view store. Three comparable runs move from
  the 9.03 s post-cache mean to 8.89 s (8.90/8.88/8.90), about 1.5%, with
  checksum `4950` unchanged. The structural view gate proves the store is
  first-class IR with no scalar helper call.
- `PROOF-1` carries exact raw-storage facts through proven object fields and
  structurally transparent direct wrappers, and turns proven named
  `buf_get`/`buf_set` calls into the same checked inline IR as `@`. In the Doom
  program, 356 named calls become 208 proven inline accesses and 148 checked
  fallbacks. Final production runs take 8.65/8.74/8.65 s user, mean 8.68 s:
  about 2.4% beyond the view stage and 6.9% across cache+view+proof. Checksum
  remains `4950`.
- The proof-stage binary is 594,777 bytes versus 578,258 after the view stage,
  a 16,519-byte (about 2.9%) code-size cost. Its symbol sample moves
  `freelang_buf_get` directionally from 349 to 208 leaves. The seven RGBX view
  stores still retain bounds checks because their clipped/branch-shaped ranges
  exceed the first affine grammar; only clean nested `pixel = y*w+x` is proved.
- Later Doom-only stages specialize the packed sky, backdrop, wall and plane
  pair loops; reserve the 64-pixel-scaled status suffix outside the 640x336
  world viewport; cache immutable status artwork; hoist stable atlas state;
  and specialize the dominant wrapped wall sampler. The evolved workload uses
  checksum `5154`; its comparable 120-frame user time reaches about 3.28--3.29
  seconds after the retained stages.
- Renderer scratch that is semantically i32 but indexed through clipped and
  branch-shaped ranges now remains measured byte ownership with local
  `%32le[]` views. Compared immediately around that stage, warm user time moves
  from about 3.42 to 3.29 seconds. A same-duration symbol sample moves checked
  `buf_get` leaves 270→168 and `buf_set` leaves 133→37 while checksum `5154`
  remains exact on ARM64 and x86-64.
- A 240-frame moving E1M2 headless route exposes a redundant per-actor
  whole-map movement scan that the stationary workload largely misses. The
  stamped wall/sprite depth buffer is already the final visual authority;
  retiring only that combat pre-scan moves mean user time 8.44→8.11 seconds
  (about 4.0%). Gameplay state is identical and both final 640x400 PPM files
  hash to `c74385011f19c20b4c033391f797340e13222bead9f60f32273df99bed706b0d`.
- An exact quotient/remainder wall-step experiment preserved checksum `5154`
  but regressed mean user time by about 11% because extra boxed scalar state
  and branches cost more than the removed divisions. It was fully discarded.
- Saved `/tmp/freelang-suite-doom-perf-20260822.txt` passes 575/575 (409 normal,
  166 expected-fail). The three symbol profiles remain under
  `/tmp/freelang-doom-profile-640*-20260822/`; the post-cache profile is
  `/tmp/freelang-doom-profile-640-cache-20260822/`.

## Separate audio finding

The silent trial was not caused by raster load. Adding all admitted monster
effects made a 37-clip bank (music plus 36 effects), beyond protocol v2's old
32-clip library bound. The client therefore refused speaker birth and Doom
continued silently as designed. The library bound is now 64 while the 32 MiB
PCM and 16 concurrent-voice bounds remain unchanged; the native driver ACKs
the exact 37-clip class and real E2M1 no longer reports silent fallback.

## Closure

The 640x400 performance campaign closes at the scratch-view and stamped-depth
checkpoints. Gameplay parity resumes next. Loop scalar promotion remains a
general compiler candidate, while native/SIMD raster kernels remain deferred
until parity is green and a concrete resolution above 640 supplies a new
application gate. A thresholded kernel should retain this Freelang renderer as
its readable differential oracle rather than replacing it.

The possible exact-width byte-pattern RHS
`rgbx@pixel = %[cr, cg, cb, 0]` is deliberately not part of VIEW-1. A later
application must earn exact-width-only semantics, dynamic length failure and
literal scalarization without allocation.
